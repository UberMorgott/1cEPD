# Партнёрское API 1С — справочник

Что это, что из него можно достать, чего нельзя, и где грабли.

Проверено живыми вызовами 02.09.2026 под партнёрским доступом. Всё, что здесь написано про форматы
ответов, получено из реальных ответов сервиса, а не из документации.

---

## 1. Коротко

`https://partner-api.1c.ru/api` — REST-сервис фирмы «1С» для партнёров.
Позволяет узнать, что происходит с вашими клиентами: есть ли у них действующий договор 1С:ИТС,
какие программы они могут использовать, сколько документов ЭДО израсходовано и на какую сумму
выставлять счёт.

Машиночитаемая спецификация: `GET https://partner-api.1c.ru/api/v3/api-docs` (OpenAPI 3, открыта без авторизации).
Интерактивная: `https://partner-api.1c.ru/api/swagger-ui/index.html`.

Есть ещё SOAP-интерфейсы (см. §9), но они дублируют часть REST и новых возможностей не дают.

## 2. Границы: что API умеет и чего не умеет

### Умеет

- Сказать статус договора 1С:ИТС по логину, регистрационному номеру или коду абонента.
- Вернуть список ваших абонентов с организациями, ИНН, КПП и регистрационными номерами.
- Сказать, есть ли у клиента доступ к конкретной программе и почему нет, если нет.
- Отдать справочник всех программ 1С и их версий с датами и требованиями к платформе.
- Построить отчёты: трафик ЭДО по клиенту, биллинг ЭДО за месяц, расход лицензий сервисов.
- Проверить, существует ли пользователь с такой парой логин + e-mail.
- Показать, какие пробные тарифы доступны абоненту.

### Не умеет

Это важнее списка возможностей, потому что определяет, что придётся делать руками.

- **Ничего не изменяет.** Ни одного метода записи. Нельзя завести клиента, привязать
  идентификатор ЭДО, продлить договор, отказаться от сопровождения.
- **Не управляет идентификаторами ЭДО.** Их видно в отчётах, но добавить, удалить или
  перепривязать через API нельзя — только вручную в Кабинете партнёра.
- **Не регистрирует договоры 1С:ИТС.** Регистрация идёт файлом-заявкой на `itsrobot@1c.ru`, см. §10.
- **Не отдаёт историю.** Всё возвращается на текущий момент. Хотите видеть, что изменилось,
  сохраняйте снимки у себя.
- **Не уведомляет.** Никаких webhook и подписок, только опрос.
- **Не ищет.** Нет поиска по названию или ИНН — только точное совпадение по логину,
  регномеру или коду абонента. Список абонентов приходится выгружать целиком и фильтровать у себя.
- **Не отдаёт цены и остатки квот напрямую.** Лимит и расход есть в отчётах, остаток
  считается вычитанием.
- **Не отдаёт биллинг ЭПД.** `/edo/reports/billing` — только пакеты ЭДО; отчёта
  «Детализация биллинга» ЭПД в API нет. Его выгружают с портала руками, см. §8.4.

## 3. Доступ и авторизация

**Схема:** HTTP Basic. Заголовок `Authorization: Basic base64(логин:пароль)`.

**Где взять:** Кабинет партнёра на `portal.1c.ru` → Администрирование → «API к Порталу 1С:ИТС».
Нужны права администратора партнёра. Логин выдаётся автоматически в формате `api-login-<код партнёра>`,
пароль генерируется там же и его можно сменить.

**Важно:** пока пароль не подтверждён кнопкой на портале, он не работает — сервис отвечает
`401 Bad credentials`, хотя пароль выглядит выданным.

Проверка доступа одной командой:

```bash
curl -u "$PARTNER_API_LOGIN:$PARTNER_API_PASSWORD" \
  -H 'Content-Type: application/json' \
  -d '{"loginList":["test"]}' \
  https://partner-api.1c.ru/api/rest/public/subscription/checkItsByLogin
```

Ответ `200` с телом `[{"status":"NoContract",...}]` означает, что доступ работает.

### Ошибки авторизации

| Ответ | Что значит |
|---|---|
| `401` `{"message":"Bad credentials"}` | неверный логин или пароль, либо пароль не подтверждён на портале |
| `403` | метод не разрешён вашему партнёрскому доступу |

## 4. Общие правила

- Все запросы, кроме двух, — `POST` с телом JSON. `GET` только у `/programs` и у получения
  готовых отчётов.
- `Content-Type: application/json;charset=UTF-8`.
- **Батчи ограничены:** проверки — не более 100 элементов за запрос, список абонентов —
  не более 300 записей на страницу, версии программ — не более 1000 за запрос.
- Даты приходят в ISO 8601 с зоной UTC: `2026-08-25T21:00:00Z`. Обратите внимание, что
  московская полночь выглядит как `21:00:00Z` предыдущего дня — при отображении переводите в свою зону.
- Формат ошибки: `{"timestamp":..,"status":..,"error":..,"message":..,"path":..}` для сбоев уровня
  Spring и `{"error":..,"message":..}` для прикладных.

### Три способа адресовать клиента

Почти каждая проверка есть в трёх вариантах, и это разные сущности:

| Ключ | Что это | Пример |
|---|---|---|
| **логин** | учётная запись пользователя на Портале ИТС | `ivanov@example.ru` |
| **регистрационный номер** | номер экземпляра программы 1С | `18117482` |
| **код абонента** | клиент целиком, с префиксом типа | `CL-1000530`, `FR-FR-600361` |

Префикс кода абонента значим: `CL-` — клиент с локальной программой, `FR-` — клиент в облаке Фреш.
От этого зависит, каким способом ему оформляется тариф ЭПД (см. §10).

## 5. Проверка договора 1С:ИТС

Три метода, отличаются только ключом.

```
POST /rest/public/subscription/checkItsByLogin           {"loginList":["логин", ...]}
POST /rest/public/subscription/checkItsByRegNum          {"regNumberList":[18117482, ...]}
POST /rest/public/subscription/checkItsBySubscriberCode  {"subscriberCodeList":["CL-1000530", ...]}
```

Ответ — массив, по элементу на каждый запрошенный ключ:

```json
[{
  "status": "NoContract",
  "code": 105,
  "description": "У пользователя нет действующего договора 1С:ИТС.",
  "login": "test",
  "itsContractInfo": []
}]
```

Поле с ключом называется по способу запроса: `login`, `regNumber` или `subscriberCode`.

**Осторожно:** в запросе регистрационный номер передаётся **числом**, а в ответе возвращается
**строкой**. Не гоняйте его через JavaScript `number`.

При наличии договора `itsContractInfo` содержит:

```json
{
  "description": "…",
  "startDate": "2025-08-25T21:00:00Z",
  "endDate": "2027-08-25T20:59:59Z",
  "itsContractType": {
    "uin": "…",
    "name": "…",
    "nameForUser": "…",
    "publicSubscriptionTypeNumber": 161
  }
}
```

### Коды статусов

| Код | Статус | Значение |
|---|---|---|
| 1 | `Success` | договор 1С:ИТС оформлен |
| 101 | `AgreementNotExists` | договор не оформлен |
| 102 | `LoginNotFound` | пользователь с таким логином не найден |
| 103 | `IsNotUser` | для этого пользователя проверка не предусмотрена |
| 104 | `OldContract` | срок действия договора завершился |
| 105 | `NoContract` | нет действующего договора |
| 108 | `SubscriberNotFound` | абонент с таким кодом не найден |
| 109 | `IsNotClient` | для абонента проверка не предусмотрена |

Неизвестный код не считайте ошибкой — показывайте как есть вместе с `description`.

## 6. Отраслевое сопровождение

```
POST /rest/public/industry/checkByLogin                     {"loginList":[...]}
POST /rest/public/industry/checkByRegNum                    {"regNumberList":[...]}
POST /rest/public/industry/checkIndustryBySubscriberCode    {"subscriberCodeList":[...]}
```

Обратите внимание на несимметричные пути: у первых двух — `checkByLogin` и `checkByRegNum`,
у третьего — `checkIndustryBySubscriberCode`.

```json
[{
  "status": "NotEmptyList",
  "code": 107,
  "description": "У пользователя есть хотя бы одна конфигурация, для которой требуется сервис 1С:ИТС Отраслевой",
  "login": "test",
  "programInfoList": [{
    "uin": "5d79b4a2-e4f4-11e0-8993-005056910018",
    "name": "1С:Учет в управляющих компаниях ЖКХ, ТСЖ и ЖСК",
    "industrySubscriptionInfoList": null
  }]
}]
```

Дополнительные коды: `106 EmptyList` — таких конфигураций нет, `107 NotEmptyList` — есть хотя бы одна.
Код 109 здесь иногда приходит со статусом `IsNotCLIENT` — с другим регистром букв, чем в проверке ИТС.
Сравнивайте по числовому коду, не по строке.

Внутри `industrySubscriptionInfoList`, когда он не пуст:
`{nomenclatureName, serialNumber, industrySubscriptionTypeInfo{description,uin}, beginDate, endDate}`.

## 7. Абоненты, программы, номенклатура

### Список абонентов

```
POST /rest/public/subscriber   {"page":0,"size":300}
```

Нумерация страниц с нуля, `size` не больше 300 и не меньше минимума (пустое тело `{}` даст `400`).

```json
{
  "subscribers": [{
    "code": "FR-FR-800918",
    "name": "Евгений Ковалев",
    "subjects": ["EDO"],
    "regNumbers": null,
    "organizations": [
      {"name": "ООО \"МАЯК\"", "inn": "7811000790", "kpp": "780001001"}
    ]
  }],
  "size": 300, "page": 0, "total": 1234
}
```

Значения `subjects` — по каким направлениям абонент обслуживается:

| Значение | Смысл |
|---|---|
| `SUBSCRIPTION` | договор 1С:ИТС |
| `APPLICATION_SUBSCRIPTION` | продажа сервиса (1С:Контрагент, 1С:Номенклатура и т. п.) |
| `INDUSTRY_SUBSCRIPTION` | сопровождение по ИТС Отраслевому |
| `EDO` | трафик по 1С-ЭДО |
| `FRESH_PURCHASE` | покупка тарифа на 1cfresh.com |
| `REPORTING_LICENSE` | сопровождение по 1С-Отчётности |

### Доступ к программам

```
POST /client-program-access/search/login        {"login":"ivanov@example.ru"}
POST /client-program-access/search/reg-number   {"regNumber":18117482}
```

```json
[{
  "regNumber": 18117482,
  "program": {"uin":"…","name":"…","nick":"TSZH1C","configurationName":"…",
              "groupProgram":false,"developerName":"…","isBase":false,
              "industryAccessCheckTime":"…"},
  "hasAccess": false,
  "missingSupportConditions": [
    {"id":"thisProgram","groupId":1,"name":"…","description":"Условие сопровождения, требующее…","displayOrder":1}
  ],
  "itsSubscriptionTypes": [{"ueid":"…","name":"…"}],
  "programIndustrySubscriptionCategories": [{"ueid":"…","name":"…"}]
}]
```

`missingSupportConditions` — готовый ответ на вопрос «почему у клиента не работает»:
перечислены недостающие условия сопровождения с человеческим описанием.

### Справочник программ

```
GET  /programs                                  весь справочник, без параметров
POST /program-versions    {"nick":"Accounting","cursor":0}
```

`/programs` отдаёт `{name, programNick, configurationName, groupName, isBasic, createdDate}`.
Справочник большой, тянуть его на каждый чих не нужно — синхронизируйте раз в сутки.

`/program-versions` возвращает `{cursor, programVersions[]}`, где версия — это
`{name, buildDate, status, platformMinVersion, platformMaxVersion, platformRecommendedVersion,
platformVersions[], previousVersions[], revocationDate, supportEndDate}`.
Статус версии: `TEST`, `PLAN`, `REVOCATION`, `FINAL`. Пагинация курсорная, не более 1000 за запрос.

### Номенклатура по регистрационным номерам

```
POST /nomenclature/getByRegNumbers    [18117482, 18117483]
```

**Внимание:** это единственный метод, который принимает **голый массив**, а не объект.
Попытка передать `{"regNumbers":[…]}` даст `400`.

```json
[{"regNum":18117482,"serialNumber":"2900001906197","name":"Облачная инфраструктура. Рабочее место…"}]
```

### Существование пользователя и пробные тарифы

```
POST /users           {"login":"ivanov@example.ru","email":"ivanov@example.ru"}   → {"found":false}
POST /trial-tariffs   {"applicationNick":"1C-Counteragent","subscriberCodeList":["CL-1000530"]}
```

Оба поля в `/users` обязательны. `applicationNick` — из фиксированного списка:
`1C-Business-Training`, `1C-Cloud-backup`, `1C-Counteragent`, `1C-Courierika`,
`1C-Document-Recognition`, `1C-ESS`, `1C-Goods`, `1C-Link`, `1C-MAG`, `1C-Nomenclature`,
`1C-OFD-receipt`, `1C-SBP`, `1C-Spark-risks`, `1C-Speech-Recognition`, `1C-Speech-Synthesis`.

## 8. Отчёты

Отчёты строятся асинхронно: сначала `POST` создаёт задачу и возвращает идентификатор,
затем `GET` по этому идентификатору забирает результат.

**Общее правило:** повторный `POST` при таймауте делать нельзя — задача могла создаться,
получите дубль и потратите часовой лимит.

### 8.1 Биллинг ЭДО — главный отчёт

```
POST /edo/reports/billing              {"date":"2026-08-01T00:00:00Z"}   → {"taskUeid":"…","error":null}
GET  /edo/reports/billing/{taskUeid}
```

`GET` отвечает `204 No Content`, пока отчёт не готов. Когда готов — отдаёт **CSV, а не JSON**:
UTF-8 с BOM, разделитель `;`, кавычки удваиваются, десятичный разделитель — запятая.

Колонки:

```
Код партнера; Название партнера; Владелец; Логин; Ид_ЭДО клиента; Наименование клиента;
ИНН клиента; КПП клиента; Тарифы ИТС; Лимит; СФ_исх; не_СФ_исх;
Кол-во пакетов документов ЭДО; Сумма пакетов документов ЭДО по владельцу; Льгота;
Количество пакетов документов ЭДО к оплате; Тариф для клиента; Сумма для клиента;
Сумма для партнера; Дополнительная информация
```

Это самый полезный источник в API. В одной таблице: идентификаторы ЭДО всех клиентов,
их владельцы и логины, лимит по тарифу, фактический расход и сумма к выставлению.

Остаток квоты считается как `Лимит` − `Кол-во пакетов документов ЭДО`.

**Что важно понимать про этот отчёт:**

- Строки с пустым `Владелец` — идентификатор без привязки к абоненту. У всех таких строк
  одновременно пусты `Лимит` и `Тарифы ИТС`: это одно и то же состояние, а не три разных.
  При этом трафик по ним идти может — в живых данных встретилась строка без владельца
  с 56 пакетами документов. Такой трафик не привязан ни к какому лимиту.
- **Арифметика между колонками не выводится.** Встречается `СФ_исх = 7`, `не_СФ_исх = 13`
  при `Кол-во пакетов документов ЭДО = 7`. Не пытайтесь досчитывать одно из другого —
  берите готовые значения.
- Колонка «Сумма пакетов документов ЭДО по владельцу» агрегатная: она относится к владельцу,
  а не к строке, и повторяется в нескольких строках одного владельца. Складывать её по строкам
  нельзя — получите двойной счёт.
- У одного ИНН законно бывает несколько идентификаторов, и у одного логина тоже —
  встречался логин с тремя идентификаторами и двумя разными ИНН. Само по себе это не аномалия.

### 8.2 Трафик ЭДО по клиенту

```
POST /edo/reports/client-traffic   {"inn":"…","login":"…","subscriberCode":"…",
                                    "periodFrom":"2026-08-01T00:00:00Z",
                                    "periodTo":"2026-08-31T23:59:59Z"}
GET  /edo/reports/client-traffic/{taskUeid}
```

Тоже CSV. Колонки:

```
Название организации; ИНН; КПП; Абонент; Оператор; Дата сопровождения с; Дата сопровождения по;
Идентификатор ЭДО; Логин; Дата создания связи; Дата регистрации идентификатора ЭДО;
СФ (вх.); не_СФ (вх.); ЭПД (вх.); СФ (исх.); не_СФ (исх.); ЭПД (исх.)
```

Здесь **ЭПД считается отдельной колонкой** от счетов-фактур и прочих документов, и здесь же
видны оператор ЭДО, дата создания связи и дата регистрации идентификатора — то, чего нет
в биллинге. Строк на клиента может быть несколько — по одной на идентификатор.

### 8.3 Биллинг опций (лицензии сервисов) — квоты

```
POST /rest/public/option/billing-report        {"type":"REPORTING","subscriberCodeList":["…"]}
GET  /rest/public/option/billing-report/{reportUeid}
```

Здесь ответ — JSON, а не CSV:

```json
{
  "reportUeid": "…",
  "state": "OK",
  "completedDate": "2026-09-02T13:45:57Z",
  "report": {"entries": [{
    "subscriberCode": "FR-FR-600361",
    "tariffs": [{
      "name": "ИТСааС ПРОФ",
      "publicSubscriptionTypeNumber": null,
      "buyDate": "…",
      "userOrganizationName": "ООО \"ВЕКТОР ФИНАНС\"",
      "userOrganizationInn": "7811000520",
      "userOrganizationKpp": "780001001",
      "startDate": "2025-08-25T21:00:00Z",
      "endDate": "2027-08-25T20:59:59Z",
      "options": [{
        "name": "Лицензия для сдачи отчетности одного юридического лица или ИП…",
        "quantitative": true, "maxVolume": 1, "usedVolume": 1
      }]
    }]
  }]}
}
```

`state`: `PROCESSING` → `OK` либо `ERROR`. Остаток квоты — `maxVolume` − `usedVolume`.

Поля, которые бывают пустыми: `publicSubscriptionTypeNumber` приходит `null` (в схеме это число —
не разбирайте его в `int`, иначе `null` превратится в `0`), `report` отсутствует при `PROCESSING`
и `ERROR`, `tariffs` и `options` бывают пустыми списками. Флаг `quantitative` различает
количественные опции (у которых есть `maxVolume`) и качественные.

Типы отчёта: `CLOUD_BACKUP`, `COUNTERAGENT`, `LINK`, `NOMENCLATURE`, `REPORTING`, `SIGN`,
`SPARK_RISKS`, `ESS`, `MAG1C`, `DOCUMENT_RECOGNITION`, `CHECK_SCAN`.

**Ошибки построения.** Приходят как `400` с кодом в теле, но означают разное:

| Код | Значение | Повтор поможет? |
|---|---|---|
| `MAX_TASKS_PER_HOUR_LIMIT_REACHED` | превышен часовой лимит запросов | да, позже |
| `MAX_NOT_HANDLED_TASKS_COUNT_REACHED` | слишком много необработанных задач | да, позже |
| `BILLING_DOES_NOT_EXIST` | биллинга нет для этих параметров | **нет** |

Первые два — временные, задача не провалилась, её нужно повторить позже.
Третий — предметная ошибка: повторять бессмысленно, надо менять запрос.
Валить их в одну кучу «повторим позже» нельзя.

### 8.4 Биллинг ЭПД — в API нет, загружается выгрузкой

Отчёта биллинга ЭПД в партнёрском API нет: `/edo/reports/billing` (§8.1) считает пакеты
ЭДО, а клиент, у которого только ЭПД, может не попасть ни туда, ни в отчёты трафика (§8.2).
Такие клиенты (в живых данных — организации нескольких владельцев Фреша `FR-FR-…`) не
видны реестру клиентов, пока не загружена выгрузка с портала 1С-ЭДО.

Выгрузка «Детализация биллинга» ЭПД — CSV с портала, тот же формат, что у §8.1
(UTF-8 с BOM, `;`, кавычки удваиваются). Колонки:

```
Код партнера; Название партнера; Владелец; Логин; Ид_ЭДО клиента; Наименование клиента;
ИНН клиента; КПП клиента; Тарифы ИТС; Лимит; Кол-во документов ЭПД;
Сумма документов ЭПД по владельцу; Льгота; Количество документов ЭПД к оплате;
Тариф для клиента; Сумма для клиента; Сумма для партнера; Исх. ЭТРН; Исх. ЭПЛ;
Дополнительная информация
```

Отличия от §8.1, которые ломают разбор, если их не знать:

- **Пустой `Владелец` — тот же владелец, что строкой выше.** Портал пишет владельца только
  в первой строке группы. В §8.1 пустой владелец значит «идентификатор не привязан» —
  переносить владельца можно только в этой выгрузке.
- `Владелец` — «`<код> - <ФИО | почта | логин>`»: у владельцев Фреша после кода обычно почта.
- Пустой `КПП клиента` — ИП.

В приложении: кнопка «Загрузить выгрузку биллинга (CSV)» на экране «Клиенты»
(`POST /api/clients/epd-import`, multipart, поле `file`). Новая загрузка заменяет прежнюю.
Клиенты выгрузки — наши; их реквизиты дополняют только пустые поля: в форме заявки
приоритет — последняя заявка, затем данные API, затем выгрузка. Владелец становится
ответственным клиента, только если после кода стоит ФИО.

## 9. SOAP-интерфейсы

Существуют, но нужны только для совместимости со старым кодом. REST покрывает всё то же и больше.

| Сервис | Endpoint | Пространство имён | Операции |
|---|---|---|---|
| subscription v1 | `/api/ws/subscription` | `http://api.repository.onec.ru` | `checkItsByRegNum`, `checkItsByLogin` |
| subscription v2 | `/api/ws/subscription/v2` | `http://api.repository.onec.ru/v2` | те же |
| industry | `/api/ws/industry` | `http://api.repository.onec.ru` | `checkIndustryByRegNum`, `checkIndustryByLogin` |

WSDL — по адресу сервиса с `?wsdl`. Стиль document/literal, `SOAPAction` пустой.
Авторизация — тот же HTTP Basic. Ошибки приходят как SOAP Fault
`AuthorizationFailedException` или `MethodAccessDeniedException`.

Отличие v2 от v1: в ответе появился блок `subscriptionTypeInfo`
(`description`, `uin`, `nameForUser`, `publicSubscriptionTypeNumber`).

Проверки по коду абонента в SOAP **нет** — она существует только в REST.

## 10. Регистрация тарифов: чего в API нет

Оформление договоров и тарифов через API невозможно. Порядок такой:

1. Заполняется файл-заявка `ip00000_ru.xls` (шаблон и правила — в Справочнике партнёра по ИТС,
   `its.1c.ru/db/partnerits`).
2. Файл отправляется на **`itsrobot@1c.ru`**.
3. Через некоторое время результат виден уже через API — у клиента появляется договор.

### Правила для тарифов 1С-ЭПД

Из инфовыпуска «1С» № 34677 от 17.07.2026.

Коды для поля «Вид 1С:ИТС» в файле-заявке:

| Код | Тариф | Код | Тариф |
|---|---|---|---|
| 2092 | ЭПД-200 | 2096 | ЭПД-7000 |
| 2080 | ЭПД-600 | 2083 | ЭПД-10000 |
| 2081 | ЭПД-1000 | 2840 | ЭПД-20000 |
| 2093 | ЭПД-2000 | 2841 | ЭПД-30000 |
| 2094 | ЭПД-3000 | 2084 | ЭПД-50000 |
| 2095 | ЭПД-4000 | 2085 | ЭПД-100000 |
| 2082 | ЭПД-5000 | | |

Обязательные условия:

- «Наименование фирмы», «ИНН» и «КПП» заполняются обязательно;
- «Количество выпусков» — строго `12`;
- «Способ оплаты» — только `1` (за весь срок сразу), помесячная оплата не допускается;
- «Дата начала» — в формате `ДД.ММ.ГГ`;
- отказы не допускаются;
- регистрационный номер программы должен быть зарегистрирован в Личном кабинете клиента;
- идентификатор участника ЭДО должен быть связан с логином этого Личного кабинета;
- в Кабинете партнёра должна быть настроена связь с клиентом по ЭДО.

**Ключевое ограничение.** Льготный лимит тарифа, оформленного файлом-заявкой, действует только
на организации, у которых код абонента-владельца идентификатора ЭДО начинается на `CL-`
(локальные программы). Для клиентов в облаке Фреш (код владельца на `FR-`) тариф оформляется
не заявкой, а подпиской в «Менеджере сервиса», и коды там другие:

`1223` ЭПД-200, `1200` ЭПД-600, `1201` ЭПД-1000, `1224` ЭПД-2000, `1225` ЭПД-3000,
`1226` ЭПД-4000, `1202` ЭПД-5000, `1227` ЭПД-7000, `1203` ЭПД-10000, `1228` ЭПД-20000,
`1229` ЭПД-30000, `1204` ЭПД-50000, `1205` ЭПД-100000.

Перепутать нельзя: заявка на клиента с владельцем `FR-` уйдёт в брак.

Трафик свыше 200 000 документов в год — индивидуальный тариф по запросу на `epd@1c.ru`.

## 11. Практические рецепты

**Узнать, у кого кончается договор.** Выгрузить абонентов постранично, затем батчами по 100
прогнать `checkItsBySubscriberCode` и отфильтровать по `endDate`. Отдельного метода нет.

**Узнать, кому выставлять счёт за ЭДО.** Построить `edo/reports/billing` за нужный месяц
и взять строки, где «Количество пакетов документов ЭДО к оплате» больше нуля.

**Найти клиентов на грани лимита.** Тот же отчёт: сравнить «Лимит» и «Кол-во пакетов документов ЭДО».

**Понять, почему у клиента не работает программа.** `client-program-access/search/login` →
`hasAccess: false` и список `missingSupportConditions` с описаниями.

**Отследить пропажу идентификатора ЭДО.** API истории не хранит. Сохраняйте ежедневный снимок
отчёта биллинга ЭДО и сравнивайте с предыдущим.

## 12. Грабли

Собрано на живых вызовах, каждая стоила времени.

1. **`/nomenclature/getByRegNumbers` принимает голый массив**, все остальные — объект.
   Универсальный сборщик тел запросов на нём сломается.
2. **Отчёты ЭДО отдают CSV, отчёт опций — JSON.** Один парсер не подойдёт.
3. **Регномер: в запросе число, в ответе строка.** Точность при этом не теряется — девять цифр
   спокойно помещаются в JavaScript `number`. Держать его строкой стоит по другой причине:
   это идентификатор, а не величина. Складывать и сравнивать по порядку его незачем,
   зато ведущие нули и единый формат в URL важны.
4. **Суммы в CSV с десятичной запятой и разным числом знаков.** В одном отчёте соседствуют
   `710,00` и `355,000`. Тип, рассчитанный на две цифры после запятой, потеряет данные.
   Храните в целых с запасом (тысячные доли рубля) или строкой, но не в `float`.
5. **`204` — это не ошибка**, а «отчёт ещё строится». И `204` на несуществующий идентификатор
   задачи выглядит так же, как на существующий, — свои задачи учитывайте сами.
6. **`GET` на SOAP-endpoint возвращает `500`**, а не `405`. Не пугайтесь.
7. **Пустое тело `{}` для `/rest/public/subscriber` даёт `400`** — `size` обязателен.
8. **Даты в UTC.** Московская полночь выглядит как `21:00:00Z` предыдущего дня.
9. **`IsNotClient` и `IsNotCLIENT`** — один код 109, разное написание в разных методах.
   Сравнивайте по числу.
10. **Сервис за DDoS-Guard.** Держите разумную частоту запросов и не открывайте много
    параллельных соединений.
11. **Неподтверждённый пароль выглядит выданным**, но даёт `401`. Кнопка подтверждения на портале.
