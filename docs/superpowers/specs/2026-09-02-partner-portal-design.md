# 1С Partner Ops — дизайн

Дата: 2026-09-02
Статус: утверждается

## 1. Проблема

Личный кабинет партнёра на `portal.1c.ru/partner` неудобен, но сам по себе он не боль.
Боль — три конкретные рабочие задачи, которые в нём решаются вручную и потому проваливаются:

1. **Отваливаются и дублируются идентификаторы ЭДО.** Строки теряют владельца, рядом заводится
   второй идентификатор на тот же ИНН. Замечают случайно, возвращают вручную.
2. **Проворонивают выставление счетов.** Клиент выходит за лимит пакетов ЭДО, это видно только
   в отчёте, который никто не строит регулярно.
3. **Вручную заполняют файл-заявку `ip00000_ru.xls`** на регистрацию 1С:ИТС — 34 колонки
   и справочник из 449 кодов.

Сервис решает эти три задачи. Справочники и карточки абонентов — подпорка к ним, а не самоцель.
Зеркалить кабинет целиком не нужно.

### Подтверждение на живых данных

Отчёт ЭДО-биллинга за 08.2026 (23 строки) уже показывает:

- 4 клиента с двумя разными `Ид_ЭДО` на один ИНН: 4200000320, 7800000720, 7811000310, 7839000949;
- 7 строк без владельца — идентификатор есть, привязки нет;
- 1 клиент за лимитом: ИНН 4200000320, 71 пакет сверх, 710 ₽ к выставлению.

## 2. Область

Внутренний инструмент одного партнёра (код 00000). Доступен из интернета.
Только чтение из 1С: сервис не изменяет данные в 1С, кроме постановки задач на построение отчётов
и генерации файла-заявки, который сервис затем сам отправляет письмом роботу «1С».

Стек задан: backend Go, frontend Vue.

### Не входит в v1 (YAGNI)

Рассылки и уведомления (сигналы живут в интерфейсе — решение заказчика), SOAP-интерфейсы 1С,
роли и права внутри приложения, конструктор отчётов, мобильная версия, автоматический возврат
идентификаторов (см. ограничение ниже).

### Жёсткое ограничение

Партнёрское API — **только чтение**. Метода записи нет ни одного. Вернуть отвалившийся идентификатор
программно через него невозможно. Сервис фиксирует пропажу, показывает прежнее значение и даёт
готовые шаги для ручного возврата. Автовозврат потребует API самого 1С-ЭДО — это другая система,
доступа к ней пока нет.

## 3. Источники данных

Base: `https://partner-api.1c.ru/api`. Auth: HTTP Basic, логин `api-login-00000`.
Спецификация: `GET /api/v3/api-docs` (OpenAPI 3). Все методы партнёру доступны — проверено.

### 3.1 Отчёт ЭДО-биллинга — главный источник

`POST /edo/reports/billing` с телом `{"date":"<date-time>"}` → `{taskUeid,error}`.
`GET /edo/reports/billing/{taskUeid}` → `204` пока не готово, затем **CSV**, а не JSON:
UTF-8 с BOM, разделитель `;`, кавычки удваиваются, десятичный разделитель — запятая.

Колонки:

```
Код партнера; Название партнера; Владелец; Логин; Ид_ЭДО клиента; Наименование клиента;
ИНН клиента; КПП клиента; Тарифы ИТС; Лимит; СФ_исх; не_СФ_исх;
Кол-во пакетов документов ЭДО; Сумма пакетов документов ЭДО по владельцу; Льгота;
Количество пакетов документов ЭДО к оплате; Тариф для клиента; Сумма для клиента;
Сумма для партнера; Дополнительная информация
```

Отсюда берётся всё для направлений 1 и 2: идентификаторы, владельцы, лимиты, расход, суммы.

`POST /edo/reports/client-traffic` с `{inn,login,subscriberCode,periodFrom,periodTo}` →
тоже CSV, детализация по конкретному клиенту, по строке на каждый идентификатор:

```
Название организации; ИНН; КПП; Абонент; Оператор; Дата сопровождения с; Дата сопровождения по;
Идентификатор ЭДО; Логин; Дата создания связи; Дата регистрации идентификатора ЭДО;
СФ (вх.); не_СФ (вх.); ЭПД (вх.); СФ (исх.); не_СФ (исх.); ЭПД (исх.)
```

Здесь **ЭПД выделен в отдельные счётчики**, чего нет в биллинге, и есть оператор ЭДО с датами
создания связи и регистрации идентификатора — это нужно для разбора аномалий.

### 3.2 Биллинг опций — квоты по лицензиям

`POST /rest/public/option/billing-report` с `{"type":<enum>,"subscriberCodeList":[str]}` → `{reportUeid}`.
`GET /rest/public/option/billing-report/{reportUeid}` →
`{reportUeid, state: PROCESSING|OK|ERROR, completedDate, report{entries[{subscriberCode, tariffs[{name, publicSubscriptionTypeNumber, buyDate, userOrganizationName, userOrganizationInn, userOrganizationKpp, startDate, endDate, options[{name, quantitative, maxVolume, usedVolume}]}]}]}}`

`maxVolume` / `usedVolume` — квота и расход по каждой опции. Остаток считается вычитанием.

Типы: `CLOUD_BACKUP`, `COUNTERAGENT`, `LINK`, `NOMENCLATURE`, `REPORTING`, `SIGN`, `SPARK_RISKS`,
`ESS`, `MAG1C`, `DOCUMENT_RECOGNITION`, `CHECK_SCAN`.
Ошибки лимитов (HTTP 400): `MAX_TASKS_PER_HOUR_LIMIT_REACHED`, `MAX_NOT_HANDLED_TASKS_COUNT_REACHED`,
`BILLING_DOES_NOT_EXIST`.

### 3.4 Файл-заявка `ip00000_ru.xls`

Формат — старый OLE2 `.xls`, версия формы 3.09, три листа:

- **Лист1** — шапка (код партнёра, пароль, ответственный, e-mail, флаги заказа сводного и детального
  отчётов 1С:ИТС) и таблица «Регистрация 1С:ИТС» на 34 колонки: № п/п, код партнёра, способ получения,
  код дистрибутора, вид 1С:ИТС, регномер, реквизиты пользователя (наименование, ИНН, КПП, рабочие места,
  вид деятельности, директор, ответственный, адрес, телефоны, e-mail), параметры сопровождения
  (операция, дата отказа, причина отказа, дата начала, количество выпусков, способ оплаты),
  до 4 регномеров других программ и регномер ПП, сданного в Upgrade.
- **Лист2** — коды причин отказа (1–5), способа оплаты (0 помесячно, 1 предоплата), операции
  (0 новая, 1 отказ).
- **Коды ИТС_сервисов** — 449 позиций «код → наименование».

### Известные подводные камни

- Формы тел запросов неоднородны: `/nomenclature/getByRegNumbers` принимает **голый массив**,
  остальные — объект. Общий «универсальный» билдер тел его сломает.
- Отчёты ЭДО отдают **CSV**, отчёт опций — **JSON**. Один парсер на оба не подойдёт.
- Регномер в запросе число, в ответе строка. Точность в JS не теряется — девять цифр помещаются
  в `number`; держим строкой потому, что это идентификатор, а не величина. В Go — `int64`.
- **Суммы в CSV — с десятичной запятой и разным числом знаков.** В одном отчёте соседствуют
  `710,00` и `355,000`. Хранить целым числом в тысячных долях рубля; `float64` и «копейки»
  одинаково непригодны.
- **Арифметика между колонками не выводится.** Встречается `СФ_исх = 7`, `не_СФ_исх = 13`
  при `Кол-во пакетов документов ЭДО = 7`. Считать одно из другого нельзя.
- **Колонка «Сумма пакетов документов ЭДО по владельцу» агрегатная**, повторяется в строках
  одного владельца. Складывание по строкам даст двойной счёт.
- **`Владелец` — составная строка** вида `FR-FR-600361 - user@example.ru`. Хранить исходную
  строку и отдельно разобранный код абонента с признаком успешности разбора.
- **ИНН не идентифицирует организацию**: филиалы делят ИНН и различаются КПП, у ИП КПП пуст.
  Ключ — пара.
- **`publicSubscriptionTypeNumber` бывает `null`** — разбирать в указатель, не в `int`.
- `BILLING_DOES_NOT_EXIST` — предметная ошибка, а не лимит: повтор не поможет.
- Неизвестный `status` или поле не должны ломать декодирование: неизвестные коды показываются
  как есть вместе с исходным `description`.
- Таймаут на POST постановки отчёта не означает, что задача не создалась. Автоповтор запрещён,
  состояние такой задачи — `outcome_unknown`, повтор только вручную.

## 4. Экраны

### 4.1 Биллинг и квоты

Таблица по конторам: наименование, ИНН, тариф ИТС, лимит, израсходовано, **остаток**,
к оплате, сумма для клиента, сумма для партнёра.

Раскрытие строки: детализация по логинам и идентификаторам этой конторы, помесячная динамика расхода,
детализация трафика (`client-traffic`) и квоты по лицензиям из `option/billing-report`
(тариф → опции с `maxVolume`/`usedVolume`).

Сверху — блок «требует действия»: кто вышел за лимит и на какую сумму, у кого остаток ниже порога
(порог настраивается, по умолчанию 10 % лимита), у кого договор ИТС кончается в ближайшие 30 дней.

Выгрузка видимой таблицы в CSV.

### 4.2 Идентификаторы ЭДО

Ежедневный снапшот отчёта ЭДО-биллинга, экран показывает расхождения между снапшотами.

#### Источник реестра

Реестра связей ЭДО в партнёрском API нет — проверены все 20 методов. Полный список живёт
в Кабинете партнёра, но автоматически его не забрать: вход защищён двухфакторной аутентификацией,
учётных данных портала у сервиса нет и не будет. Скрапинг кабинета исключён.

Поэтому реестр **накапливается самим сервисом** из двух доступных отчётов:

| Источник | Что даёт | Ограничение |
|---|---|---|
| `edo/reports/billing` за закрытый месяц | все идентификаторы с начислениями, владельцы лимитов, ИНН, КПП, логины | текущий месяц недоступен: `BILLING_DOES_NOT_EXIST` |
| `edo/reports/client-traffic` без фильтра по клиенту, за широкое окно | оператор ЭДО, дата создания связи, дата регистрации идентификатора, счётчики ЭПД отдельно | только те, у кого был документооборот |

Проверено на живых данных: биллинг за август дал 23 идентификатора, трафик за два с половиной
года — 15, и все они входят в первый набор. То есть биллинг полнее, трафик добавляет к нему даты
и оператора.

Сервис ведёт собственную таблицу `edo_identifiers`: каждый идентификатор с датой первого и
последнего появления, всеми известными атрибутами и историей их изменений. Это одновременно
и реестр для сравнения, и то самое резервное хранение данных клиентов, ради которого всё затевалось.

**Честное ограничение, которое нужно проговорить пользователям:** клиент, у которого нет ни
начислений, ни документооборота, для API невидим. Про такого сервис узнает только когда у него
появится хоть какая-то активность. На скриншоте кабинета 24 организации, в биллинге за август —
23 строки; разницу закрыть нечем.

#### Чего структура данных не позволяет

Отличить легальный дубль от поломки автоматически **невозможно**: ни биллинг, ни отчёт трафика
не содержат вида деятельности организации, а именно он объясняет законные дубли.
Проверено на живых данных: у одного ИНН законно бывает несколько идентификаторов, и у одного
логина тоже — встретился логин с тремя идентификаторами и двумя разными ИНН.

Отсюда два следствия. Первое: сигналы ранжируются по уверенности, а не делятся на «поломка»
и «норма». Второе: нужен **реестр ожидаемой топологии** — таблица `организация → идентификатор →
назначение`, которую заполняют люди, отмечая известные им законные связи с причиной и автором.
Без него любой алгоритм будет либо шуметь, либо пропускать.

#### Сигналы по убыванию уверенности

**1. Идентификатор без владельца, но с трафиком.** Документы идут, а лимита, к которому их
отнести, нет. В живых данных такой один: 56 пакетов мимо всякого тарифа.
Проверять просто: `Владелец` пуст и `Кол-во пакетов документов ЭДО` больше нуля.

Уточнение по смыслу поля: `Владелец` в биллинге — это абонент, которому принадлежит **лимит
по тарифу**, а не признак живой связи с клиентом. Проверено: четыре строки с пустым владельцем
присутствуют в отчёте трафика, и там у них заполнен «Абонент». Поэтому сигнал означает
«трафик не покрыт тарифом», а не «связь слетела» — это тоже деньги, но другой природы.

**2. Владелец был и пропал.** Переход состояния между снимками, а не само состояние.
Самый достоверный признак того, что связь именно слетела.

**3. Идентификатор исчез из отчёта.** Подтверждается только двумя последовательными полными
снимками — один сбой на стороне 1С не должен объявлять весь реестр пропавшим.
До подтверждения находка живёт в состоянии «подозрение».

**4. Замена.** Если у той же организации или того же логина одновременно пропал старый
идентификатор и появился новый — это одно событие `replaced`, а не две несвязанные тревоги.

**5. Идентификатор без владельца и без трафика.** Наблюдение, не тревога. В живых данных таких
шесть, и они, судя по всему, лежат так давно. Показываются отдельным списком.

Важно: у всех строк без владельца одновременно пусты `Лимит` и `Тарифы ИТС`, а у всех строк
с владельцем лимит заполнен. То есть «без владельца», «без лимита» и «без тарифа» — одно
и то же состояние, а не три независимые проверки.

Критерий «дубль без трафика» из первой версии спеки отвергнут: он пропустил бы находку №1,
где сломанный идентификатор как раз с трафиком.

#### Подтверждение и подавление

Каждая находка хранит **отпечаток состояния** — набор полей, на основании которых она возникла.
Пометка «это законно» гасит находку только для этого отпечатка: если состояние изменится
(появится трафик, сменится логин, пропадёт владелец у другой строки), сигнал возникнет снова.
Подавление по паре «ИНН + идентификатор» без отпечатка скрыло бы будущую настоящую поломку.

У пометки есть автор, причина и дата пересмотра — раз в полгода подавленные находки
показываются для перепроверки.

#### Карточка находки

Что было, что стало, когда изменилось, степень уверенности и шаги для ручного возврата:
логин, по которому искать, и прежний идентификатор для сверки. История изменений по каждому
идентификатору хранится целиком.

Второй источник для сверки — отчёт `client-traffic`: в нём есть оператор ЭДО, дата создания связи
и дата регистрации идентификатора, которых нет в биллинге. Плюс кнопка «Выгрузить все условия
сопровождения в CSV» в Кабинете партнёра даёт третий срез, его можно загружать вручную файлом.

### 4.3 Заявки 1С:ИТС

Форма, повторяющая Лист1 файла-заявки, но с подстановками:

- реквизиты клиента подтягиваются из `subscriber` и `checkIts*` по ИНН/логину/регномеру;
- вид 1С:ИТС выбирается из справочника 449 кодов с поиском по названию;
- коды причины отказа, способа оплаты и операции — выпадающие списки с расшифровкой из Лист2;
- шапка (код партнёра, ответственный, e-mail) заполняется из конфигурации.

Заявка хранится в БД как черновик, редактируется, затем выгружается файлом с именем
`ip<первые 5 цифр кода партнёра>.xls`. Отправку на `itsrobot@1c.ru` сервис выполняет сам:
тот же файл уходит вложением в письме по SMTP, а факт отправки отмечается в `sent_at`.
Почтовый ящик, порт (465 сразу по TLS или 587 через STARTTLS), логин, пароль приложения,
адрес отправителя и список получателей задаются на экране «Настройки» и лежат в БД,
а не в переменных окружения: почту меняют без перезапуска сервиса.

Полные правила заполнения — в [REQUESTS.md](../../REQUESTS.md). Главное для реализации:

- **структуру шаблона менять нельзя** — заполняется существующий файл, а не создаётся похожий;
- продажи идут по тарифам 1С-ЭПД, поэтому «Вид 1С:ИТС» ограничивается 13 кодами
  (`2092`, `2080`, `2081`, `2093`, `2094`, `2095`, `2082`, `2096`, `2083`, `2840`, `2841`, `2084`, `2085`);
- для ЭПД «Количество выпусков» принудительно `12`, «Способ оплаты» принудительно `1`,
  ИНН и КПП обязательны, отказы запрещены;
- «Дата начала» для сервисов — `ДД.ММ.ГГ`, для обычного ИТС — `ММ.ГГ`; формат подставляется
  по виду услуги, вручную не вводится;
- **блокирующая проверка:** если код абонента-владельца начинается на `FR-`, заявка не выпускается —
  для Фреша тариф оформляется в Менеджере сервиса другими кодами. Владелец берётся из отчёта
  биллинга ЭДО;
- проверки перед выпуском: регномер зарегистрирован в ЛК клиента
  (`client-program-access/search/reg-number`), идентификатор ЭДО связан с логином этого ЛК
  (по отчёту `edo/reports/client-traffic` за год) — обе выполняются через API перед сборкой
  файла и перед отправкой. Блокирует только определённый отрицательный ответ; если 1С
  недоступна или логин не указан, замечание приходит с отметкой «не проверено»
  и выпуск не останавливает.

#### Формат файла

Формат строго `.xls` (BIFF8), тот же, что у присланного шаблона `ip00000_ru.xls` вер. 3.09.
`.xlsx` не подходит.

Зрелой библиотеки записи BIFF8 с сохранением оформления на Go нет: `excelize` пишет только
`.xlsx`; `extrame/xls` и `shakinm/xlsReader` умеют исключительно чтение. Поэтому шаблон правится
точечно своим кодом: при изменении длины потока пересчитываются смещения, которые от неё
зависят (BOUNDSHEET, INDEX, DBCELL, EXTSST), а контейнер OLE2 собирается заново.

Порядок заполнения:

1. Шаблон `assets/ip00000_ru.xls` хранится в репозитории и не меняется.
2. Сервис на Go раскладывает данные заявки по ячейкам шаблона.
3. Пакет `internal/xlsfill` правит копию шаблона на уровне записей BIFF8: вписывает значения,
   сохраняя XF каждой ячейки, дописывает строки в SST и пересчитывает сдвинутые смещения.
   Структура, названия, оформление и расположение полей не меняются — правятся только значения.
4. Результат отдаётся пользователю под именем `ip<код партнёра>.xls`.

Заполнение идёт внутри процесса сервиса: внешних утилит, Python или LibreOffice не нужно.

Проверено на настоящем шаблоне: все три листа сохраняются, таблица регистрации остаётся на
34 колонки, справочник кодов из 449 строк цел, записанные значения читаются обратно.
Файл при этом ужимается с 217 до 114 КБ — теряется часть оформления, в первую очередь
комментарии-подсказки к ячейкам, которые роботу не нужны.

**Обязательная проверка перед выпуском в работу:** отправить одну настоящую заявку на
`itsrobot@1c.ru` и дождаться протокола с `autoits@1c.ru`. Заполнение шаблона теряет часть
оформления, а робот отвергает файлы с изменённой структурой. Пока протокол не получен,
направление считается непроверенным.

### 4.4 Абоненты и проверка (подпорка)

Таблица абонентов с поиском по названию/ИНН/коду и карточка абонента: статус ИТС расшифрованный,
отраслевой доступ, номенклатура по регномерам, доступ к программам с причинами отказа.

Отдельная форма проверки: одно поле, тип определяется автоматически (только цифры 8–9 знаков →
регномер; префикс `PR-`/`FR-`/`CL-` → код абонента; иначе логин), тип можно переопределить.
Выполняются проверки ИТС + отраслевой + доступ к программам. Поддержка пакетного ввода, батчи по 100.

### 4.5 Резервная копия данных клиентов

Отдельного экрана нет — это следствие снапшотов. Всё, что приходит из 1С (абоненты, организации,
логины, идентификаторы ЭДО, регномера, договоры), сохраняется в свою БД с историей.
Если данные в 1С пропали, видно последнее известное состояние и дату.

**Пароли клиентов в БД не хранятся.** Если они нужны — только ссылка на внешний менеджер паролей.

### Хранение

SQLite в режиме WAL. Один инстанс, один партнёр — Postgres здесь только эксплуатационный налог.

| Таблица | Назначение |
|---|---|
| `sessions` | `token_hash, created_at, expires_at, ip, user_agent` — много одновременных сессий |
| `edo_snapshots` | `id, kind (billing\|traffic), period, taken_at, row_count, csv_sha256, is_baseline, raw_csv`; уникальность по `(kind, period, csv_sha256)` — повторно полученный тот же отчёт нового снимка не создаёт |
| `edo_identifiers` | накопленный реестр: `edo_id, inn, kpp, client_name, login, owner_raw, owner_code, operator, link_created_at, id_registered_at, first_seen_at, last_seen_at, last_source`. Пополняется из обоих отчётов, служит и реестром для сравнения, и резервной копией |
| `edo_rows` | разобранные строки снапшота: партнёр, владелец, логин, `edo_id`, клиент, ИНН, КПП, тариф, лимит, расход, к оплате, суммы. Индексы по `edo_id`, `login` и паре `(inn, kpp)` |
| `identifier_events` | `at, edo_id, inn, kpp, kind (orphan_with_traffic\|owner_lost\|disappeared\|replaced\|orphan_idle), confidence, state_fingerprint, before_json, after_json, confirmed_at` |
| `identifier_acks` | `edo_id, state_fingerprint, reason, author, acked_at, review_at` — отметки «это законно», привязанные к отпечатку состояния |
| `expected_topology` | `inn, kpp, edo_id, purpose, note, author, updated_at` — реестр известных законных связей, заполняется людьми |
| `option_reports` | результаты `option/billing-report` по типам, с датой |
| `subscribers_snapshot` | абоненты и организации с историей — резервная копия |
| `programs`, `program_versions`, `sync_state` | справочник программ |
| `report_jobs` | `id, kind, upstream_id, request_json, status, result_blob, error, created_at, updated_at` |
| `its_requests` | заявки: `id, title, status (draft\|exported), schema_ver, revision, payload_json, created_at, updated_at, exported_at, sent_at`. Отдельного статуса `sent` нет: отправку отмечает `sent_at`, потому что письмо уходит по уже выгруженной заявке и статус для этого заводить незачем. `schema_ver` нужен, потому что форма заявки меняется (сейчас 3.09), `revision` защищает от параллельного редактирования |
| `settings` | настройки почты, строка ровно одна (`CHECK(id = 1)`): `smtp_host, smtp_port, smtp_login, smtp_password_enc, smtp_from, mail_to` (JSON-массив), `updated_at`. Пароль лежит зашифрованным AES-256-GCM, ключ — файл `secret.key` рядом с базой, поэтому дамп базы сам по себе пароль не выдаёт |

На лету, без БД: точечные проверки ИТС/отраслевого, доступ к программам, номенклатура.
Поверх них TTL-кэш в памяти: успешный ответ 10 мин, ошибка 60 с.
Ключ — метод плюс нормализованный payload.

В каждом экране показывается «актуально на <время>» и кнопка принудительного обновления.

### Фоновые задачи

- **Ежедневный снапшот** ЭДО-биллинга: строит отчёт, дожидается, разбирает CSV, пишет `edo_snapshots`
  и `edo_rows` одной транзакцией, сравнивает с предыдущим снапшотом, пишет `identifier_events`,
  публикует событие. Правила:
  - пустой отчёт (заголовок без строк) — признак сбоя, не сохраняется: затирать историю нельзя;
  - отчёт, побайтово совпавший с предыдущим за тот же период, снимка не создаёт и события не шлёт;
  - первый снимок периода помечается `is_baseline`, сравнение для него не выполняется;
  - сравниваются только снимки **одного периода**: августовский и сентябрьский наборы —
    разные реестры, разница между ними ничего не значит;
  - пропажа подтверждается двумя последовательными полными снимками.
- **Воркер отчётов**: незавершённые `report_jobs` опрашиваются с backoff 2/5/10/20/30 с.
  После рестарта работа продолжается — поэтому нужна БД, а не map в памяти.
  Статусы: `pending` → `running` → `done` | `failed` | `rate_limited`.
  Одновременных upstream-задач не более двух. Повторный upstream POST автоматически не выполняется.
- **Синхронизация справочника программ**: при старте и раз в сутки, версии — лениво по `nick`, TTL 24 ч.

### Живые обновления (SSE)

`GET /api/events` — поток `text/event-stream`, одно соединение на вкладку, требует сессии.

- Реализация на stdlib: канал на подписчика плюс `http.Flusher`. WebSocket не нужен — поток
  односторонний.
- События: `report.updated`, `snapshot.completed`, `identifier.alert`, `programs.synced`,
  `cache.invalidated`.
- Keep-alive комментарием раз в 25 с, чтобы прокси не рвал соединение.
- Фронт переподключается с backoff, на время разрыва показывает индикатор «нет связи».
- Если SSE недоступен (прокси режет поток) — автоматический откат на опрос раз в 5 с.

### Аутентификация

Одна пара логин/пароль на всех сотрудников, произвольное число одновременных сессий.

- Логин и bcrypt-хеш пароля — из переменных окружения. Таблицы пользователей нет.
- `POST /api/login` при успехе выдаёт случайный 32-байтный токен, в БД хранится только его SHA-256.
  Прежняя сессия, если её предъявили, при входе гасится: навязанный до входа токен не должен
  стать рабочим после.
- Cookie: `HttpOnly`, `Secure` (выключается только для локального http), `SameSite=Strict`, TTL 30 дней, скользящий: каждый запрос продлевает срок (запись в базу не чаще раза в 10 минут).
- Защита от CSRF — той же cookie плюс проверка заголовка `Sec-Fetch-Site` на небезопасных методах:
  `SameSite` считает «сайт» по домену без порта, и соседний порт того же хоста он не отсекает.
  Токена CSRF нет, состояние хранить не нужно.
- Ограничение попыток на `/api/login` двойное. По адресу клиента — блокировка: 5 неудач
  за 5 минут, дальше `429` до конца окна. По логину — не блокировка, а растущая задержка ответа
  `2^(N-1)` секунд с потолком 30 с: учётная запись одна на всех, и блокировка по логину дала бы
  любому, кто его знает, запирать вход всем коллегам. Неудача считается по обоим ключам
  независимо от того, существует логин или нет, поэтому задержка не подсказывает, угадан ли он.
- CSP без внешних источников (шрифт лежит в самом `dist`), `X-Frame-Options: DENY`,
  `nosniff`, `Referrer-Policy: no-referrer`. Файл базы — права `0600`.
- TLS терминируется обратным прокси (Caddy или nginx). Приложение слушает localhost.
- Креды 1С существуют только на бэкенде, во фронт и в логи не попадают.
  Тела запросов целиком не логируются.

### Хранение персональных данных

В базе оседают наименования организаций, ИНН, КПП, логины клиентов, контактные данные
и сырые CSV-отчёты. Это персональные и коммерческие сведения, поэтому:

- **срок хранения**: сырые CSV — 13 месяцев (год плюс запас на сверку), разобранные строки
  и события по идентификаторам — 3 года, `audit_log` — 1 год. Старше — удаляется фоновой задачей;
- **резервное копирование**: ежедневная копия файла базы средствами SQLite (`VACUUM INTO`)
  в отдельный каталог, хранить 30 копий. Без этого «резервное хранение данных клиентов»,
  ради которого всё затевалось, само окажется единственной точкой отказа;
- **доступ к файлу базы**: каталог с правами только для учётной записи сервиса;
- шифрование самой базы в v1 не делается: это требует отдельной сборки SQLite и усложняет
  восстановление. Защита — на уровне доступа к серверу. Если заказчику нужно шифрование,
  это отдельное решение, и его надо принять до накопления данных.

### Frontend (Vue 3)

Vue 3 + Vite + TypeScript + Vue Router + Pinia + PrimeVue.

- PrimeVue выбран за DataTable с раскрытием строк, фильтрами, серверной пагинацией
  и виртуальным скроллом — ровно то, что нужно табличной админке.
- Pinia нужен: поток SSE — общее изменяемое состояние, которое видят несколько экранов
  (сигналы по идентификаторам, статусы отчётов, индикатор связи, отметки актуальности).
- Интерфейс полностью реактивный: фильтры и поиск применяются на лету (`computed` плюс debounce
  250 мс для серверных запросов), статусы меняются сами по событию, устаревание данных
  показывается живым таймером «актуально N минут назад». Кнопка обновления есть, но не является
  единственным способом получить свежие данные.
- Загрузка каждого блока — независимое состояние (`idle | loading | ready | error`),
  скелетоны вместо блокирующих спиннеров.
- Все обращения к 1С идут только через свой бэкенд.

## 6. Обработка ошибок

- Ошибка одного блока не роняет экран: блок показывает своё сообщение и кнопку повтора.
- Ошибки 1С раскладываются на: сеть или таймаут, `401` (проблема с кредами), `400` (плохой запрос,
  показывается текст 1С), лимиты построения отчётов, `5xx`. У каждой свой текст и рекомендация.
- `rate_limited` — отдельный статус, не `failed`, с текстом «превышен часовой лимит 1С».
- Единый формат ошибок API: `{"error":{"code":str,"message":str,"details":obj}}`.
- Неизвестный код статуса 1С ошибкой не считается: показывается как есть вместе с `description`.

- Фронт: без юнит-тестов в v1, проверка вручную по сценариям.

## 8. Порядок реализации

Заказчик выбрал общий каркас с последующей параллельной работой над тремя направлениями.

1. Каркас: конфиг, SQLite и миграции, сессии, вход, health, шина событий, SSE.
2. `internal/partner`: HTTP-клиент, DTO, парсер CSV, фикстуры, расшифровка статусов.
3. Снапшоты ЭДО-биллинга и воркер отчётов.
4. Направление 1: сравнение снапшотов, экран идентификаторов.
5. Направление 2: экран биллинга и квот с раскрытием строк.
6. Направление 3: справочник кодов, форма заявки, выгрузка файла.
7. Подпорка: абоненты, карточка, проверка, справочник программ.
8. Сборка одним бинарником, `embed` фронта, инструкция по развёртыванию за обратным прокси.

## 9. Открытые вопросы

1. **Что означает параметр `date`** в `POST /edo/reports/billing`: состояние на дату, отчётный
   месяц целиком или день? Может ли готовый отчёт быть неполным? Меняется ли отчёт за закрытый
   месяц? От этого зависит вся схема сравнения снимков — без ответа проектировать diff нельзя.
2. **Примеры от людей: 5–10 законных дублей и 5–10 настоящих поломок** с объяснением, чем они
   отличаются. Это единственный способ настроить пороги, структура данных различить их не даёт.
3. **Реквизиты для заявки, которых нет в API**: количество рабочих мест, директор, почтовый адрес,
   телефон, тип деятельности. Откуда их брать — вести у себя, спрашивать у клиента каждый раз,
   или они лежат в том самом резервном хранении?
4. **Где сейчас лежит резервное хранение** данных клиентов — заказчик говорит, что оно уже
   где-то есть. Нужно понять, дублировать его или заменить.
5. **Кому выставляется счёт** при перерасходе — клиенту напрямую или через партнёра, и кто
   принимает решение. От этого зависит, что показывать в блоке «требует действия».
6. **Допустима ли задержка подтверждения в сутки** для сигнала о пропаже идентификатора.
   Если нужно быстрее — придётся снимать снапшот чаще, а это упирается в часовые лимиты 1С.
7. **Глубина истории** биллинга: только текущий месяц или помесячная динамика расхода.
8. **Доступ к API 1С-ЭДО** — если он есть, автоматический возврат идентификаторов становится
   возможен. Через партнёрское API это невозможно.

### Закрытые вопросы

- **Формат заявки** — строго `.xls` (BIFF8), тот же, что у присланного шаблона вер. 3.09.
  Готовых Go-библиотек для записи BIFF8 нет, поэтому шаблон правит свой пакет `internal/xlsfill`, см. §4.3.
- **Адрес робота** — `itsrobot@1c.ru`, протокол приходит с `autoits@1c.ru`.
- **Поля «Пароль» и «Новый пароль»** — не пароль портала и не пароль API, а необязательный пароль
  подтверждения подлинности заявки (5–20 латинских букв и цифр, по умолчанию пустой).
  Автоматически не подставляется.
- **Правила кодов ЭПД** получены из инфовыпуска № 34677 от 17.07.2026, правила заполнения —
  из «Справочника партнёра». Сведены в [REQUESTS.md](../../REQUESTS.md).
  Отмечено расхождение: справочник знает только коды `2080`–`2085`, инфовыпуск добавил ещё семь;
  источник истины — инфовыпуск.
- **ЭПД или ЭДО** — ЭПД является частью ЭДО. Отдельного источника не нужно, но в отчёте
  `client-traffic` есть отдельные счётчики «ЭПД (вх.)» и «ЭПД (исх.)», в биллинге их нет.
- **Дубли идентификаторов** — бывают легальными (разные виды деятельности), сигналом сами
  по себе не являются. См. §4.2.
